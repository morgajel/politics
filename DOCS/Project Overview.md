# Project Overview

## 1. Project Overview & Scope Definition

### 1.1 Problem Statement & Objectives
* **Problem Statement:** Voters and researchers need a clear way to compare how two U.S. politicians vote on the same legislation, using attributable data from government and non-government sources.
* **Primary Objectives:**
  * Build a TypeScript application hosted on GitHub Pages.
  * Support U.S. politicians only for the initial release.
  * Allow users to select exactly two politicians for comparison.
  * Calculate and display an overall agreement score based on comparable roll-call votes.
  * Show the underlying votes, source attribution, timestamps, and unavailable-data states.
  * Keep the architecture extensible for future topic, bill, ideology, and party-alignment analysis.

### 1.2 MVP Scope and Acceptance Criteria
* **In scope:** Politician search, two-person selection, shared vote matching, overall agreement calculation, vote-level evidence, responsive presentation, accessibility, and source links.
* **Out of scope:** Topic-level analysis, ideology scores, party-leadership alignment, state/local politicians, non-U.S. politicians, and multi-politician comparison.
* **Acceptance criteria:**
  * A user can select two U.S. politicians and receive a deterministic agreement percentage.
  * Only votes with comparable, normalized outcomes contribute to the score.
  * Abstentions and absences have no impact on the agreement score and are excluded from its numerator and denominator.
  * The interface identifies the vote population, date range, data freshness, and source for every result.
  * Missing, conflicting, rate-limited, or stale data produces an understandable UI state rather than a misleading score.
  * The application works as a static GitHub Pages deployment without exposing API credentials.
  * Core normalization and agreement logic has automated unit tests.

### 1.3 Prioritization Rule
* **Priority:** FIFO (first-in, first-out) for competing requests unless a security, data-integrity, or deployment blocker requires immediate handling.

## 2. Technical Architecture & Stack

### 2.1 Tech Stack Selection
* **Frontend:** TypeScript with Vite and a lightweight component approach; choose React only if the repository's UI complexity justifies it.
* **Hosting:** GitHub Pages, using a static build.
* **Data format:** Versioned, normalized JSON contracts for politicians, votes, and vote records.
* **Testing:** Vitest for unit tests; browser smoke tests may be added after the core workflow exists.
* **Quality tooling:** ESLint and Prettier, configured to run locally and in GitHub Actions.

### 2.2 Architectural Considerations
* GitHub Pages cannot safely store API keys or run a server-side request proxy. The MVP must use browser-safe public endpoints or a separately authorized static-data publishing process.
* Near-real-time behavior will be implemented as a hybrid: fetch directly from APIs that support CORS and require no secret, while retaining a generated static snapshot fallback. The UI must display the actual data timestamp and freshness state.
* API adapters must be isolated from domain logic so Congress.gov, Voteview, GovTrack, or other sources can be replaced without rewriting comparison calculations.
* A normalization layer must map provider-specific vote values to a common outcome model such as `yes`, `no`, `present`, `abstain`, and `not-voting`; non-comparable outcomes must be excluded explicitly.
* The agreement score is defined as: comparable matching votes divided by total comparable votes, multiplied by 100. Abstentions and absences have no impact and are excluded from both the numerator and denominator.
* All displayed records need provenance: provider, source URL or identifier, retrieval time, and the relevant vote date.

## 3. Work Breakdown Structure (WBS) & Delivery Timeline

### 3.1 Work Breakdown Structure
1. **Discovery and data contract**
  * Confirm the initial congressional scope and supported offices/chambers.
  * Select providers based on coverage, freshness, licensing, CORS, rate limits, and stable identifiers.
  * Define normalized politician, vote, and comparison-result schemas.
2. **Data integration spike**
  * Build one provider adapter and test representative responses.
  * Verify browser access, pagination, rate limits, missing records, and provider failure behavior.
  * Decide whether the fallback snapshot is generated by GitHub Actions or maintained through another approved static publishing process.
3. **Comparison domain logic**
  * Normalize politician identities and vote outcomes.
  * Match shared votes by stable legislation/vote identifiers.
  * Calculate agreement and produce explainable vote-level evidence.
4. **Static frontend**
  * Implement politician search and exactly-two selection.
  * Implement comparison summary, vote table, loading, empty, stale, error, and rate-limit states.
  * Add responsive layout, keyboard navigation, semantic labels, and accessible status messaging.
5. **Freshness and deployment**
  * Add live-fetch timeout and fallback behavior.
  * Add freshness metadata and visible last-updated status.
  * Configure GitHub Pages build and deployment.
6. **Validation and release**
  * Add unit, contract, and browser smoke tests.
  * Validate representative politicians, edge cases, and mobile layouts.
  * Document data sources, methodology, limitations, and refresh behavior.

### 3.2 Milestone Schedule
| Milestone | Deliverable | Exit criteria |
| :--- | :--- | :--- |
| M1: Scope and contracts | Provider decision and normalized schemas | Data fields, identifiers, outcome rules, and MVP boundaries approved |
| M2: Provider spike | Working adapter with fixtures | Representative responses parse correctly and failure modes are documented |
| M3: Comparison engine | Tested agreement calculation | Matching, missing data, and excluded outcomes produce expected results |
| M4: MVP interface | Two-politician comparison workflow | User can select two people and inspect the score and evidence |
| M5: Freshness and deployment | GitHub Pages build with live/fallback behavior | Static deployment succeeds without secrets and exposes freshness metadata |
| M6: Release validation | Test and methodology documentation | Quality checks pass and known limitations are visible |

## 4. DevOps, Quality Assurance, & Delivery Pipeline

### 4.1 Source Control Strategy
* **Branching Model:** Local edits only for the agent; the repository owner controls commits, branches, and pull requests.
* **Pull Request Requirements:** When the owner chooses to use pull requests, require successful automated checks and review before merging.

### 4.2 Quality Assurance Strategy
* **Unit Testing:** Target >= 80% code coverage on core domain logic.
* **Integration Testing:** Validate provider fixtures, response contracts, normalization, identity matching, and fallback behavior. No database is required for the static MVP.
* **Static Analysis:** Automated linting and formatting checks; dependency and secret scanning before deployment.
* **Accessibility:** Keyboard-only workflow, semantic structure, visible focus, sufficient contrast, and screen-reader status announcements.
* **Validation checklist:** Test two valid politicians, no shared votes, missing votes, abstentions and absences excluded from scoring, provider failure, stale snapshot, API rate limiting, duplicate identities, and mobile viewport behavior.

## 5. Risk Assessment & Mitigation Matrix

| Risk ID | Description | Severity | Likelihood | Mitigation Strategy |
| :--- | :--- | :--- | :--- | :--- |
| **R-01** | Unclear third-party API specifications | High | Medium | Execute proof-of-concept spike prior to core development phase. |
| **R-02** | Scope expansion during mid-sprint | High | High | Enforce strict MVP boundaries; defer non-critical items to backlog. |
| **R-03** | CI/CD pipeline deployment failures | Medium | Low | Maintain environment parity between staging and production; implement rollback automation. |
| **R-04** | Performance bottlenecks under load | Medium | Medium | Implement early profiling, query optimization, and caching strategies. |
| **R-05** | GitHub Pages cannot provide a private API proxy or guaranteed near-real-time server execution | High | High | Prefer CORS-enabled public reads; publish static snapshots as fallback; show freshness clearly; never place secrets in frontend code. |
| **R-06** | Different providers disagree on politician or vote identifiers | High | Medium | Maintain canonical identifiers, provider mapping tables, provenance, and contract fixtures. |
| **R-07** | Agreement score is misleading because absences or abstentions are handled inconsistently | High | Medium | Publish the scoring methodology, make outcome rules explicit, and exclude non-comparable votes from the denominator. |
